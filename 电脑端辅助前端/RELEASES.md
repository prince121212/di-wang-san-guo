# 版本记录

## 开发中

V0.0.3 发布后的后续优化在此累计。

### Android 手机本地 V1

- Android 正式架构从“电脑端 Mobile API 遥控”切换为手机本地核心：APK
  打包同一套单容器前端，本机消息桥连接 Kotlin 账号、配置、调度、协议和
  本地地图；电脑关机时仍可独立运行。
- 密码与 Session 认证字段使用 Android Keystore + AES-GCM 分仓保存，账号
  JSON 和导出不再包含认证秘密；添加账号需明确凭据授权，删除账号同步
  删除密码和 Session 密文，日志统一脱敏。
- Keystore 别名升级到 V2；旧设备密钥无法解锁时清理明文并要求重新登录，
  不让本地 Activity 因 UserNotAuthenticatedException 崩溃。
- 移除生产源码中的远程核心、电脑设置、代理/VPN、协作地图、旧原生页面和
  生产 Mock；正式调度只接受启用且拥有真实 Session 的本地账号。
- 前台服务改为按任务绝对截止时间自适应唤醒，空闲期间释放 WakeLock，仅在短执行窗口持有有超时短锁；任务
  停止锁、重试/睡眠截止时间和每日完成状态可在进程重建后按配置签名恢复。
- 前台通知显示账号和当前任务并保留停止入口；通知权限与电池优化豁免只在
  用户点击启动托管后请求。
- 删除全局 TLS 信任绕过，恢复 Android 平台证书链和主机名校验；连接完成后
  主动释放，请求健康记录按执行线程绑定账号，避免多账号串账。
- 六部因缺少逐项真机动作证据不进入正式任务，手机控件保持禁用；打矿撤防
  历史配置在计划入口强制归零，不能进入未实现协议路径。
- 自动验证基线：Android 399 项、共用前端 470 项全绿；V1 覆盖审计通过。
  逐功能真实动作、6 小时锁屏、网络切换、Session 过期、重启恢复和抓包仍
  需用户明确授权后真机验收，当前不宣称 15 条标准全部完成。

- “常规-常用”的自动加体改为账号级共用出征预检：副本、无损、
  掠夺、打矿和刷黄在检查到将领体力低于用户设定阈值时，均先用
  1 枚活血丹再继续状态/配兵检查；运行中任务每次检查都读取最新公共
  设置，同一将领的并发检查会合并，避免重复消耗活血丹。
- 修复 0x8004 将领解析把体力上限 301 以上的合法将领过滤掉的问题；测试账号
  1608600 的英雄页已从 8 条恢复为接口返回的 11 条。
- 军情页新增“辅助此刻行动”实时区块：从任务引擎本地状态汇总刷黄在途
  编队（几级山贼、坐标、battleId）、副本关卡战斗（第几章第几关，0x8600
  看不到的信道）、打矿驻守和正在准备中的出征；状态以心跳里将领真实
  忙闲（征/战/防/返）定名，每 2 秒随任务轮询更新、每秒原地刷新时长，
  不新增任何游戏服务器请求。0x1600/0x8600 服务器军情分区展示，刷新
  节奏保持“进入页面和手动刷新”不变。
- 按军情专项抓包（20260726_173635）升级 0x8600 解析：副本关卡战斗
  （【副本】targetType=0x0e）与多人副本建队“备战”态、山贼去程尾部
  0x0b、行军中与战斗中按剩余行军时间区分出“出征”态、targetType
  0x03=山贼；修正 marchValue 语义为“剩余行军毫秒”（连续刷新递减），
  军情卡片“剩余时长”倒计时按 快照时刻+剩余 锚定，每秒刷新。
- 副本章末关是多人副本，单人无法挑战：打通模式自动跳过章末关直达
  下一章第一关（修复日志中“副本未确认启动成功：多人副本创建成功”
  的卡死），出征接口对章末关直接拒绝，前端关卡下拉不再提供章末关；
  记录解散组队接口 0x193a/0x893a（只记录，不主动调用）。
- 运行日志按受众分流：日志行在写入时声明是给用户看还是给排障看，未声明
  一律算排障。保存设置底部的黑框和运行日志页只显示用户行（出征、领取、
  使用道具等成功记录，以及功能暂停/无目标/恢复的播报），系统日志侧栏仍
  保留全部明细。此前结构化事件在没有 message 字段时会把整个 JSON 当成
  一行展示给用户——实测占黑框 50% 的行数、76% 的字符，其中 597/772 条只是
  RUNNING 进度心跳。两类日志各有独立保留额度，排障刷屏不再挤掉用户历史。
- 状态播报只报“持续成立”的情况：刷黄每几秒重扫一次目标，曾在四分钟内
  在“无目标/运行中”之间翻转十二次，每次都是真实状态变化却毫无信息量。
  停摆类结论立即播报，采样类状态需持续满一分钟才播报。
- 打矿出征现在有成功记录：成功记录改为按“出征已被服务器确认”这一证据
  识别，不再逐功能写分支——打矿整天都在出征却一条记录都没有，就是因为
  它的分支从来没人写。打矿/掠夺同时补上“编队N > 目标(x，y)”的编队号，
  历史账本里已确认的打矿出征也会在记录页补齐。
- 等待中的常驻任务必须交还账号车道：只要功能声明了“下次什么时候再看我”，
  调度器就把它记成该功能的车道截止时间，而不是听凭各功能自己记得声明。
  此前打矿一个驻守闭环（行军 675 秒 + 驻守/撤防/回闲）会吃掉全部 tick，
  测试账号 1608601 上副本逾期 41 分钟、刷黄逾期 104 分钟，账本里打矿
  112 个 tick 对副本 33 个。同时修正饥饿判定：通过 pending 路径占用车道
  也算“已被服务”，否则打矿跑完闭环后仍被判为饥饿，再靠优先级赢回车道。
- “停下，需要人工”同样要写进账本：功能拒绝动作（例如打矿撤防回执没有
  确认 battleId，读多少次都settle不了，禁止自动重发）时，这个结论以前
  只存在于返回值里，下一个 tick 看到的记录和正常记录没有区别，于是每
  两秒重算一次同样的拒绝并继续占着车道。现在结论落到记录上，功能进入
  既有的隔离路径并在界面上标为“需人工核对”，而不是表现为“正在忙”。
- 打矿补上闭环后半程的记录：出征之后的 驻守→撤防→整队回闲 此前不产生
  任何记录，面板上只看得到出征然后就没声音了。现在撤回完成单独记一条
  “编队N 已撤回 > 目标(x，y)”，用 `mine:recall:{battleId}` 作去重键，
  与出征记录并存而不是互相覆盖。撤防本来就是按 battleId 一次撤回整个
  编队的全部将领，这次只是把它变成看得见的事实。
- 打矿占领成功/失败按证据判定，失败进“角色-提示”：赢和输在结束那一刻
  长得一模一样——将领都回家了。区别只在过程中出现过一次：占领成功会有
  【驻守】，失败则直接【返回】。因此每次军情观察都会把证据累加到待决
  记录上，收尾时直接读结论，而不是从结束状态倒猜。两端的提示页都是从
  用户日志文本派生的，所以失败会被叙述成“打矿：编队N 占领失败，将领已
  自行返回 > 目标(x，y)”，由此出现在提示页；下一轮成功的撤回记录会把它
  清掉。军情期间从未看到过这一轮（重启、刷新丢包）时结论是“未知”，
  不报失败——误报一次不存在的失败比不报更糟。
- 撤防改由将领状态裁决，不再由回执的 battleId 裁决：0x8526 的回执里带的是
  一整份军情快照，其中【返回】事件报的 battleId 和出征时的不是同一个
  （实测发出 41604347、回来 41605271），于是每一轮都卡在“回执未确认”，
  而将领其实早就离开矿点回家了。撤防请求本身带精确 battleId，撤错队在
  请求侧就不可能，所以回执匹配仍算确认、不匹配则记为“已发送待观察”，
  改看将领是否离开“防”——只有撤防生效才会让一个将领离开驻防。将领仍在
  驻防且超过宽限期才交人工，任何情况下都不会自动重发。被拒的回执原文
  一并留存在待决账本里，下次不匹配可以直接查而不用再猜。
- 同类隐患一并修掉（与上面几条同源，都是"结论没落到账本上"或"同一个事实
  被两处各答一遍"）：
  - 内政会复现打矿那次的"每两秒重算同一个拒绝并独占车道"：将领维护/内政/
    背包整理把发送边界存在记录顶层之下，这个事实在异常处理和隔离闸门两处
    各写了一遍，后者只认将领维护。现在两处共用同一个判断。
  - 掉线重连不再丢弃上一会话的结论：原本用白名单搬运，方向反了——结论必须
    被"记得"才能活下来，而忘记是静默的。体力暂停（缺活血丹暂停 30 分钟）
    就在名单外，于是每次重连都解除暂停、立刻再撞体力不足、再写一次暂停；
    测试机 Wi-Fi 每晚断一次，这是个循环不是边角情况。现在默认全部继承，
    本次登录重算的值照常覆盖。
  - 日常任务自我暂停不再静默：日常是七件独立调度的事，状态在下一层，顶层
    播报循环既找不到 lastState 也找不到"日常"的名字，于是签到/领币/俸禄
    因回执不明停摆整个周期时日志上一个字都没有。现在每件事用自己的名字
    播报和恢复。
  - "人工确认修复"的入口不再被一张四项别名表限制在副本/无损/刷黄。
- 一个任务停摆不再拖累其他任务：此前"是否停下"靠 state 字符串是否恰好叫
  "blocked" 判断，于是每起一个新名字就重新掉进同一个坑——副本连续三次未
  确认通关时停在 clear-unconfirmed，既拿不到重试退避也保不住阻塞时刻，
  被当成"立刻就绪"每个 tick 参与竞争；它的出征又是已确认的 accepted，
  发送边界闸门也放行，于是每两秒重算一次同样的拒绝还占着车道。现在
  "需要人工"是记录上的独立事实，调度器按事实而不是按名字判断。
  区分"停摆空转"和"多步轮次正在推进"用的是账本有没有实质变化：将领维护
  每一步被拒也会写"需要人工"，但它每次都在账本里落下新的一步，所以照常
  推进；真正原地不动的才退避，期间车道归其他到期任务。
- 手机熄屏进入 Doze 后不再让副本/刷黄饿死（V0.0.73–V0.0.74）：测试机 01:59
  熄屏、02:32 进入 Deep Doze 后，核心每个 tick 都声明"立刻再来"，主机却在
  每个 tick 结束就释放唤醒锁，CPU 随即休眠，只能靠闹钟兜底，而闹钟在 Doze
  里迟到 5s–195s；tick 从 2 秒一次变成 40s–5min 一次。打矿一轮 13 分钟只要
  6–8 个 tick，天然耐受；副本一轮 2.5 分钟要 ~10 个 tick，刷黄每 tick 只
  扫 5 个坐标，于是整夜打矿 34 条、副本 13 条、刷黄 10 条。
  原则：时序正确性来自 Handler，Handler 只在 CPU 醒着时走；闹钟是进程被杀
  时的恢复手段而不是计时器。所以**调度器在自己规划视野（5 分钟）内报出的
  任何截止时刻，CPU 都必须持有到那一刻**；只有"视野内没有任何已知截止"
  （`nextDelayMillis` 返回上限值）才释放交给闹钟。规则从调度器语义推出，
  不用固定秒数——固定 60 秒今天碰巧够用只是因为探活间隔是 60 秒。
  配套三条不变量：续租直接在持有的锁上重新计时、不经过释放态（原先先释放
  再获取，Deep Doze 里 CPU 在释放的同一毫秒就休眠，正在执行的操作被冻在中
  间，一次出征拖到两分钟）；续租只能延长不能缩短（操作租约和调度持锁是两
  个独立理由，取较长者）；每个 tick 开始时保证自己有完整窗口。
  强制 Deep Doze（`dumpsys deviceidle force-idle`）实测 3 分钟 49 个 tick、
  最大间隔 11 秒、0 条调度逾期，副本在 Doze 中跑完整轮；此前同状态 3 分钟
  约 2 个 tick。
- 打矿达到资源点上限时不再白扫地图：上限检查原本只在发送边界（扫图、云端
  预占之后），满员时每 10 秒完整扫一遍再被拒。现在在扫图之前按账号事实决
  定，满员进入 capacity-full 状态、按探活刷新节奏（60s）复查，并向用户播报
  "打矿已暂停：资源点数量已满(5/5)，等待矿点数量回落后自动继续"，回落后
  播报"打矿已恢复运行"。发送边界的检查保留为最后防线，两处读同一个事实。
- 配兵不足不再被当成"未确认操作"交人工（V0.0.75）：测试机 06:11 打矿出征前
  先治疗（一条请求，回执受理），随后配兵预检发现智步1比保存的配兵少 12 名
  近卫兵、拒绝出征——之后什么都没发。但打矿/掠夺/无损/副本四个 workflow 都把
  "预检期间发过任何请求"当成"结论不明"，把记录连同 requiresAttention 留在活
  账本里，发送边界探针于是每个 tick 隔离打矿，提示页写着"存在未确认操作，
  已隔离并禁止自动重发，请人工核对"——而账号持有人唯一能做的是招兵或调低
  数字，提示里一个字没提；唯一的出口是手改 JSON。
  原则：待决记录的存在只为防止"结论未知的操作"被重放，寿命就是"某个结论未
  知"的那段时间。`OperationKnownFailureError` 按构造就是这段时间的终点——每
  个预检步骤只在发送前、或收到说明服务器做了什么的回执后才抛它；没有回执
  是 `OperationUncertainError`，走的是另一条路。所以已知失败 ⇒ 没有东西在飞
  ⇒ 记录关闭，与之前是否发过治疗无关。刷黄早就这样写了（记录归档为审计历
  史），现在五处共用一个函数；旧版本留下的这类记录在恢复路径上第一眼就被
  结清（正式出征从未发送 + 无待决预检变更），并写"此前的隔离已解除"。
  配兵不足本身按缺活血丹的同一形状处理：编队暂停 30 分钟后自动重试（兵不
  会自己长，但每 10 秒重读一遍兵营也学不到新东西），暂停账本记下原因，体
  力恢复不会误解除兵力暂停、将领维护也不会因兵力暂停跳过加体。调度器给这
  类"资源暂停"一个自己的状态 formation-paused（不是故障，也不再是静默的
  retry），播报"打矿已暂停：打矿出征前配兵未完成：将领智步1缺少12近卫兵（保
  存的配兵为699，当前空闲可用687），请在游戏内招募近卫兵或调低该将领的配兵
  数量；所在编队已暂停至HH:MM，之后自动重试"，重新出征后播报"打矿已恢复运
  行"；手机端提示页把"已恢复/已解除"也视为该条提示的结束。
- 角色-宝物页显示背包格子占用（如 49/50）和装备栏（V0.0.76）：0x8104 的"背包
  容量"此前读的是 payload 第 14–16 字节，三个真实账号解出 1863 / 1386 / 1150，
  而游戏显示的上限是 50。逆向出的原版客户端读法是 readLong、readLong、readShort
  ——两个资产计数器再接条目数——所以那两个字节只是第二个 long 的低半截；上限在
  装备记录之后的 trailer 第一个 short（两份真实抓包都是 `0032 01f4 000a 05`），
  逆向字典把 footer 里看到的 50 记到了错误偏移，parity fixture 又按这个误解手工
  造了一份没有 trailer 的报文。服务器不下发"已占格数"，只分别给道具条目数和装备
  条目数，游戏客户端自己相加——共享核心现在也这样算（用声明的计数，不用解析出
  的行数，认不出模板的装备同样占格）。上限读不到时记为未知而不是 0。
  装备栏的数据（名称/品质/强化/等级）解析器早就解出并透出到 `inventory.equipment`，
  只是页面只画了道具；现在同一张表分"道具（N 种）/装备（N 件）"两段，相同模板同
  品质同强化的装备合并成一行计件，搜索同时覆盖两段，顶部徽标显示"格子 49/50"，
  满格转红。登录路径和刷新路径的背包投影收敛为同一个函数（登录那份此前漏写了
  条目计数）。Kotlin 侧那份重复的 0x8104 解析器同步改为读 trailer。
- 一件限时道具不再让整个背包"看不见"（V0.0.77）：道具表每行是 u16 id、u16 数量、
  再加一个每行 long——原版客户端把它当数据读（时效/唯一 id），通常为 0。解析器
  此前把"这 8 字节必须为 0"当成版图校验，于是只要背包里有一件带值的道具，整包就
  退回扫描兜底：装备列表变空、上限读不到，页面显示"已占 43 格（上限未知）"，而

  上，改为校验这个；装备区对不上时若每行 long 仍全为 0（旧校验依赖的佐证），照
  旧接受并报 equipmentParseError，否则才退回扫描。
- 服务器随包下发的背包同步不再被丢弃（V0.0.77）：开箱、用道具、丢弃这些改变背包
  的操作，回包里本来就附带一份完整 0x8104。此前只当诊断数据留着，导致两处过期：
  宝物页显示的是上一次显式刷新看到的背包（真机上差了一小时）；更要紧的是背包整理
  得出"背包当前没有需要处理的物品"后睡 1 小时，而副本每几分钟开一次箱——一把
  Lv.1 普通短剑在清理结束一分钟后掉进 41/50 的背包，就会一直躺到下一个整点，尽管
  保存的规则（普通/良好、小于36级）正好选中它。现在这份证据在两条传输路径上被
  统一吸收：刷新投影（宝物页随之实时），并且只有在格子数变多、且整理正处于
  "无事可做"的休眠时才提前唤醒（变少是它自己干的活，轮次进行中不打断）。整个过程
  是纯记账，任何异常只记日志，不会把一次已受理的游戏操作变成失败。

- 本项目自己的消耗用 D1 的 `d1QueriesAdaptiveGroups` 按 SQL 归因后定位到地图
  共享，**同一个结构性错误重复了四次**：客户端刚提交的、已知的小 JSON 被当成
  "过滤条件"去筛整张表，而不是当成"驱动"去命中索引。
  - `map_target_regions` 的链接清理写成 `WHERE EXISTS (SELECT 1 FROM
    json_each(?) ...)`，于是每行链接都要重扫一遍整个 payload：每次观测读 10,040
    行，占整个账户读取量的 58%。改为从 `json_each` 驱动 JOIN，按区域索引寻道。
  - 孤儿目标清理是 `WHERE server_key=? AND map_kind=? AND NOT EXISTS(<链接>)`，
    为了找出个位数的消失目标而扫过该服全部 3,414 个目标。候选其实是已知的：
    就是本次重扫区域里的那些链接。同样改为 JSON 驱动，并移到链接清理之前
    （它需要那些链接来定位候选）。
  - SQLite 对虚拟表没有统计信息，会把实体表选作外层循环——用 `CROSS JOIN`
    固定连接顺序才真正生效；这一点靠 EXPLAIN QUERY PLAN 验证，不能想当然。
  - `idx_map_target_regions_scan` 不覆盖 `target_id`，SQLite 宁可只约束 2 列走
    主键自动索引也不愿回表，寻道退化成扫描。把 `target_id` 加进索引尾部后，
    才是"4 列全约束 + 覆盖"。
  - 目标查询 `ORDER BY last_seen_at DESC LIMIT n` 用不上
    `idx_map_targets_available(server_key,map_kind,status,last_seen_at)`：跨三个
    status 时 last_seen_at 只在各 status 内部有序，只能全取再排序（读 3,317 行
    返回 481）。换成 `idx_map_targets_recent(server_key,map_kind,last_seen_at
    DESC)`，计划里的 `USE TEMP B-TREE FOR ORDER BY` 消失。索引数量没增加。
  - 真实量级（80 格 × 42 目标）实测：旧 81.8ms → 新代码旧索引 54.6ms →
    新代码新索引 14.3ms，**5.7×**，删除结果逐行一致。
