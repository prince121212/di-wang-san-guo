## 2. 总体判断

### 2.1 小黄点有状态规则

小黄点确实有大量动作前状态判断规则，例如：

- 功能是否开启。
- 今日次数是否达到上限。
- 铜钱是否足够。
- 是否需要治疗。
- 是否选择了出征编队。
- 编队/将领是否空闲。
- 体力是否满足配置。
- 是否需要加体。
- 是否需要配兵。
- 目标是否搜索到。
- 出征是否成功。
- 失败后是否换下一组编队。
- 没有空闲将领时是否等待返回。

这些规则是我们自研辅助必须借鉴的核心。

### 2.2 但不是严格生产级统一状态机

从目前证据看，小黄点更像：

```text
每个业务任务内部各写一套 if/else 过程式规则
  -> 读配置
  -> 查状态
  -> 校验条件
  -> 执行动作
  -> 按日志/返回值进入下一步
```

不像：

```text
统一 StateStore
统一 State schema
统一 Guard 表
统一 Transition 表
统一 Action executor
统一 Retry/Rollback/Idempotency 机制
统一资源冲突管理
```

所以对自研辅助来说，不能机械复制小黄点的代码结构，而应该复制它的“业务经验”，再工程化成我们自己的动作前状态检查框架。

## 3. 小黄点整体托管机制

从逆向证据看，小黄点后台托管大致是以下模式：

```text
账号登录 / 重登
  -> 周期性后台服务
  -> 按功能开关决定是否执行任务
  -> 每个任务读取自己的配置 key
  -> 刷新/读取角色、将领、军队、资源等状态
  -> 检查前置条件
  -> 条件不足时先执行修正动作
  -> 修正失败则停止当前任务或换下一组
  -> 条件满足后发真实 game command
  -> 根据响应/日志决定继续、等待、换方向、换编队或停止
```

关键特征：

1. **以配置 key 驱动任务**。
2. **以服务器状态/解析模型作为动作前判断依据**。
3. **以日志字符串标记当前业务分支**。
4. **大量使用“失败换下一组”策略**。
5. **没有空闲资源时等待，而不是强行发包**。
6. **真实动作前通常要经过编队选择、状态检查和资源检查**。

## 5. 小黄点的“状态机”本质

### 5.1 更准确的定义

小黄点所谓状态机，本质更接近：

```text
任务动作前状态检查器 + 任务内分支决策器
```

而不是单独的一张全局状态流转图。

每个动作都需要先看状态。例如刷黄：

```text
派将领 A 带 10 个轻骑兵去刷黄
  -> 将领 A 是否空闲？
  -> 将领 A 体力是否足够？
  -> 不够是否允许使用体力丹？
  -> 当前统兵兵种是不是轻骑兵？
  -> 当前统兵数量是不是 10/最大统兵？
  -> 目标黄是否符合筛选条件？
  -> 条件满足后才 prepare + expedition
```

这些状态大部分已经在自研 App 的页面中有对应展示：

- 「角色 - 英雄」：将领态、兵种类别、等级、体力、忠诚、统兵、兵力。
- 「角色 - 军队」：编队、将领、状态、兵种、兵力。
- 「刷黄」：目标类型、等级范围、搜索坐标、次数限制、编队选择。

### 5.2 小黄点状态规则不是抽象类，而是业务分支

当前证据看到的是很多业务日志和配置 key，例如：

- `不是空闲状态，不可出征。`
- `不是空闲状态，不能出征。换下个编队。`
- `体力不足设置的`
- `配兵失败(可能配兵时正在出征)，不可出征。`
- `配兵失败，不能出征。换下个编队。`
- `有空闲将领，开始下一次刷黄`
- `没有空闲将领了，等待将领返回...`

这说明小黄点确实在动作前做状态判断，但目前没看到它有一个独立、统一、可复用、强约束的 StateMachine 类或状态 DSL。

## 6. 动作前状态检查通用模型

自研辅助应把小黄点的经验抽象为统一模型：

```text
ActionPlan
  -> StateSnapshot
  -> Preconditions
  -> RepairActions
  -> Recheck
  -> RealAction
  -> ResultParser
  -> NextDecision
```

含义：

| 层 | 说明 |
|---|---|
| `ActionPlan` | 用户想执行的动作，例如“刷黄一次”、“打矿一次”、“闯关一次” |
| `StateSnapshot` | 当前状态快照，来自角色/英雄/军队/资源/地图/目标查询 |
| `Preconditions` | 动作前置条件，例如空闲、体力、兵种、兵量、铜钱、次数 |
| `RepairActions` | 可自动修正动作，例如用体力丹、治疗、配兵、换编队 |
| `Recheck` | 修正后必须重新读取状态确认 |
| `RealAction` | 真实发包动作，例如找黄、prepare、出征 |
| `ResultParser` | 解析返回结果，例如成功、失败、目标失效、资源不足 |
| `NextDecision` | 下一步：继续、等待、换方向、换编队、停止、重登 |

## 7. 刷黄机制细节

### 7.1 刷黄主流程

小黄点刷黄大致流程：

```text
读取 openShuaHuang
  -> 未开启：提示“设置里未开启刷黄功能”，结束
读取 shuahuangcounts / 今日次数
  -> 达上限：提示“刷黄次数已满/今日刷黄次数已达到”，结束
读取铜钱 / shuaHuangTongQianLimit
  -> 铜钱不足：停止刷黄
读取刷黄出征编队 shuahuangChuzhengBiandui
  -> 未选择：提示“目测你没有选择任何刷黄出征编队！”
检查是否有空闲将领/编队
  -> 有：开始下一次刷黄
  -> 无：等待将领返回
按配置找山贼/黄巾
  -> 没找到：换方向找 / 提示没有搜索到符合条件的山贼
找到目标
  -> 选择刷黄出征编队
  -> 出征成功：继续搜索
  -> 出征失败：换下一组编队
```

### 7.2 刷黄目标搜索

相关证据：

- 固定 hex 模板：`000000000000000000041540`
- 业务字符串：
  - `正在搜索符合条件的`
  - `[山贼]`
  - `[黄巾]`
  - `...(目前除繁体版是黄巾外其余一律设置为『山贼』)`
  - `搜索山贼进度：`
  - `换个方向找...`
  - `没有搜索到符合条件的山贼...`

自研借鉴：

```text
找黄不能只发一次固定坐标。
应该按方向/范围/等级条件持续扫描，并且在没有空闲将领时暂停扫描或等待。
```

### 7.3 刷黄出征协议

已确认 payload builder：

```text
prepare/first = 000000000000000000 + hex(ids.size * 8 + 0x0a) + 1520030 + ids.size(decimal) + concat(ids) + 0000 + targetId

expedition/second = 000000000000000000 + hex(ids.size * 8 + 0x15) + 1522030 + ids.size(decimal) + concat(ids) + 0000 + targetId + ffffffffffffffff000000
```

其中：

- `1520030`：刷黄 prepare。
- `1522030`：刷黄 expedition。
- `ids`：出征将领/编队相关 id 列表。
- `targetId`：找黄得到的目标 id。

自研侧已经通过 direct-binary game command 验证了刷黄闭环，不依赖小黄点 native wrapper。

### 7.4 刷黄前置条件

自研应实现的刷黄前置条件：

| 检查项 | 状态来源 | 通过条件 | 不通过处理 |
|---|---|---|---|
| 功能开关 | 刷黄配置 | 已开启 | 不执行 |
| 今日次数 | 本地配置 + 服务器/日志计数 | 未达上限 | 停止刷黄 |
| 铜钱 | 角色/资源状态 | 大于阈值 | 可先治疗/换粮，失败则停止 |
| 编队选择 | 刷黄配置 | 至少一个候选编队 | 提示配置错误 |
| 将领状态 | 角色-英雄 / 角色-军队 | 空闲 | 等待返回或换下一组 |
| 体力 | 角色-英雄 | 足够 | 使用体力丹，复查 |
| 兵种 | 角色-军队 | 符合配置，例如轻骑兵 | 改统领兵种，复查 |
| 兵量 | 角色-军队 | 符合配置，例如 `10/198` | 调整兵量，复查 |
| 目标 | 找黄结果 | 符合等级/类型/距离条件 | 继续搜索或换方向 |
| prepare | 协议返回 | 成功 | 换目标/换编队/停止 |
| expedition | 协议返回 | 成功 | 计数 + 继续/停止 |

## 8. 配兵、治疗、体力机制

### 8.1 配兵

逆向证据中的相关字符串：

- `开始配兵`
- `配兵完成！`
- `配兵失败`
- `配兵失败，不能出征。换下个编队。`
- `配兵失败(可能配兵时正在出征)，不可出征。`
- `补满失败，将领可能未配兵`

说明小黄点在出征前不是默认相信配置，而是会尝试确保编队/将领符合出征要求。

自研借鉴：

```text
出征前必须检查当前兵种和兵量。
如果不符合任务配置，应先配兵。
配兵后不能直接出征，必须重新读取“角色-军队”状态确认。
```

刷黄例子：

```text

当前：将领 A 空闲，但统兵=步兵 3000/198
动作：改统领轻骑兵，并设置 10/198
复查：角色-军队显示轻骑兵 10/198
通过：执行找黄/出征
```

## 12. 失败处理策略

小黄点的失败处理很值得借鉴。

### 12.1 换下一组

相关日志：

- `刷黄出征失败！换下一组编队`
- `打矿出征失败！换下一组编队`
- `掠夺出征失败！换下一组编队`
- `出征失败，换下个编队`

自研规则：

```text
如果某个编队/将领动作失败，不要立刻停止整个任务。
优先将该候选标记为本轮失败，切换下一组候选。
```

### 12.2 等待返回

相关日志：

- `没有空闲将领了，等待将领返回...`
- `刷黄编队里没有空闲将领，等待将领出征返回...`
- `打矿编队里没有空闲将领，等待将领出征返回...`
- `闯关编队里没有空闲将领，等待将领返回...`

自研规则：

```text
当所有候选都不空闲时，不应强行发包。
进入 WAITING_FOR_IDLE，下一轮刷新英雄/军队状态后再判断。
```

注意：这里的 `WAITING_FOR_IDLE` 是我们自研工程上的状态表达，小黄点证据中未必有同名抽象状态。

### 12.3 搜索换方向

相关日志：

- `换个方向找...`
- `没有搜索到符合条件的山贼...`
- `没有搜索到符合条件的矿...`

自研规则：

```text
地图搜索应有方向/半径/进度，不应单点失败就停止。
```

### 12.4 异常停止

相关日志：

- `刷黄异常，启动失败。`
- `打矿异常，启动失败。`
- `副本异常，启动失败。`
- `闯关异常，启动失败。`
- `日常异常，启动失败。`
- `内政异常，启动失败。`

自研规则：

```text
不可修复异常应停止对应任务，不要影响整个账号所有任务，除非 session 已失效或登录状态异常。
```

## 13. 防封 IP / 登录失败提示机制

小黄点中存在关于 IP 被封/频繁登录的提示：

```text
登录失败，IP被封 (或者可能区服正在维护中)！
可能该IP登录过于频繁或没有防封IP，导致IP被封，请更换IP(移动网络可以开关一下飞行模式，WiFi重启路由器)后再登录。
防封IP措施：
① √选防封IP设置；
② 按实际情况设置延迟时间100～800毫秒；
③ 同区同一个网络下只挂机一个号，且不同时玩其余号。
```

借鉴点：

1. 登录失败不一定是账号密码错，也可能是 IP/维护/频率问题。
2. 产品上需要区分：账号密码错误、区服名错误、IP 被封/维护、掉线。
3. 多号托管需要延迟/错峰，避免同区同网同时登录多个号。
4. 自研辅助可以做“防封提示/节流策略”，但不要承诺绝对防封。

## 14. 小黄点机制强弱点评估

### 14.1 优点

1. **实战经验丰富**：覆盖刷黄、打矿、掠夺、闯关、治疗、配兵、加体等大量场景。
2. **动作前判断充分**：不是盲发包，会检查开关、次数、资源、编队、空闲状态。
3. **失败处理实用**：失败换下一组，没空闲等待，资源不足停止。
4. **日志明确**：大多数业务分支都有中文日志，利于用户理解。
5. **任务分支完整**：刷黄/打矿/闯关都有搜索、选择编队、出征、失败处理链路。

### 14.2 不足

1. **工程抽象不强**：未看到统一状态机框架。
2. **规则分散**：规则散落在各任务方法里，复用性弱。
3. **依赖日志推断**：当前逆向成果很多是字符串证据，部分控制流还需继续深挖。
4. **生产级严密性不足**：未看到统一幂等、回滚、事务、并发资源管理。
5. **状态 schema 不完整**：我们仍需继续解析 `0x8004` 等响应字段，才能完整还原英雄/军队状态。

## 15. 自研辅助应如何借鉴

### 15.1 不照抄小黄点结构

不要直接照搬“小黄点每个任务一堆 if/else”的结构。这样后续刷黄、打矿、副本、日常会越来越难维护。

### 15.2 抽象成动作前状态检查框架

建议自研统一实现：

```kotlin
data class ActionContext(
    val account: AccountSession,
    val state: StateSnapshot,
    val config: TaskConfig,
    val candidate: ActionCandidate
)

interface Precondition {
    fun check(ctx: ActionContext): CheckResult
}

interface RepairAction {
    suspend fun repair(ctx: ActionContext): RepairResult
}

interface TaskAction {
    suspend fun execute(ctx: ActionContext): ActionResult
}
```

执行链：

```text
refreshState()
  -> buildCandidate()
  -> checkPreconditions()
  -> repairIfPossible()
  -> refreshStateAgain()
  -> executeRealAction()
  -> parseResult()
  -> decideNext()
```

### 15.3 先实现刷黄状态检查

刷黄优先落地以下规则：

1. 读取刷黄开关。
2. 读取每日次数限制。
3. 读取角色铜钱/粮食。
4. 读取候选将领/编队。
5. 检查将领状态是否空闲。
6. 检查体力。
7. 体力不足则使用体力丹。
8. 检查当前兵种。
9. 兵种不对则改兵种。
10. 检查当前兵量。
11. 兵量不对则设置为配置值，例如 `10/198`。
12. 复查英雄/军队状态。
13. 找黄。
14. prepare。
15. expedition。
16. 记录成功次数。
17. 决定继续/停止/等待。

### 15.4 状态来源优先级

状态来源应按优先级处理：

1. **服务器最新响应**：例如登录后 `0x1016 -> 0x8004`。
2. **动作响应**：例如出征成功/失败响应。
3. **本地任务内临时状态**：例如本轮某编队失败、某目标已尝试。
4. **配置状态**：例如期望兵种/兵量/次数。
5. **UI 展示状态**：用于产品展示，不能反过来当唯一事实来源。

## 17. 自研刷黄状态检查伪代码

```kotlin
suspend fun runBrushYellowOnce(account: Account): TaskDecision {
    val state1 = protocol.refreshState(account) // 0x1016 -> 0x8004
    val config = configRepo.getBrushYellowConfig(account.id)

    if (!config.enabled) return TaskDecision.Stop("设置里未开启刷黄功能")
    if (config.todayCount >= config.dailyLimit) return TaskDecision.Stop("刷黄次数已满")
    if (state1.money < config.minMoney) return TaskDecision.Stop("铜钱不足，停止刷黄")

    val candidate = selectCandidateFormation(state1, config)
        ?: return TaskDecision.Sleep("刷黄编队里没有空闲将领，等待将领出征返回...")

    if (!candidate.isIdle) {
        markCandidateSkipped(candidate, "不是空闲状态")
        return TaskDecision.Continue("换下一组编队")
    }

    if (candidate.stamina < config.minStamina) {
        val ok = protocol.useStaminaItem(account, candidate.generalId)
        if (!ok) return TaskDecision.Continue("体力不足，换下一组编队")
    }

    if (candidate.soldierType != config.requiredSoldierType) {
        val ok = protocol.changeSoldierType(account, candidate.generalId, config.requiredSoldierType)
        if (!ok) return TaskDecision.Continue("改兵种失败，换下一组编队")
    }

    if (candidate.soldierCount != config.requiredSoldierCount) {
        val ok = protocol.setSoldierCount(account, candidate.generalId, config.requiredSoldierCount)
        if (!ok) return TaskDecision.Continue("配兵失败，换下一组编队")
    }

    val state2 = protocol.refreshState(account)
    val checked = verifyCandidateAfterRepair(state2, candidate, config)
    if (!checked) return TaskDecision.Continue("修正后复查失败，换下一组编队")

    val target = protocol.searchYellow(account, config.searchArea, config.targetFilter)
        ?: return TaskDecision.Continue("没有搜索到符合条件的山贼，换个方向找...")

    val prepared = protocol.prepareBrushYellow(account, candidate.ids, target.id)
    if (!prepared.success) return TaskDecision.Continue("刷黄 prepare 失败，换下一组编队")

    val sent = protocol.dispatchBrushYellow(account, candidate.ids, target.id)
    if (!sent.success) return TaskDecision.Continue("刷黄出征失败！换下一组编队")

    return TaskDecision.Continue("刷黄出征成功！继续搜索...")
}
```

## 19. 最终借鉴原则

一句话：

> 小黄点值得借鉴的是“业务状态判断经验”，不是它的代码组织方式。

自研辅助应该比小黄点更清晰：

```text
小黄点：任务内 if/else + 日志 + 轮询 + 发包
自研：统一状态快照 + 前置条件 + 自动修正 + 复查 + 动作执行 + 决策器
```

最终目标：

```text
每个真实动作执行前，都能回答：
1. 当前状态是什么？
2. 前置条件是否满足？
3. 不满足能否自动修正？
4. 修正后是否复查通过？
5. 是否允许真实发包？
6. 发包失败后下一步是什么？
```

这才是我们要从小黄点中迁移出来，并且工程化升级的核心机制。
