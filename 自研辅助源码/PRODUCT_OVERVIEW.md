# 帝王三国自研辅助产品说明文档

> 版本：v0.3（刷黄闭环真机验证后）  
> 项目：`自研辅助源码`  
> 当前目标：把“小黄点辅助”的运行机制、状态机和核心协议能力逐步迁移到自研辅助中。

---

## 1. 产品定位

本产品是一个面向《帝王三国》的账号托管辅助工具。它不是简单的“点按钮发包器”，而是由以下几层组成的后台托管系统：

1. **账号 / 登录 / session 管理层**：保存账号、区服、登录状态、真实 session、角色基础信息。
2. **角色状态层**：通过 `0x1016 -> 0x8004` 获取角色、资源、将领、编队等状态。
3. **任务配置层**：每个账号拥有独立配置，例如刷黄次数、起始坐标、编队、目标类型。
4. **后台调度层**：前台点击“启动”后，由 ForegroundService 周期执行任务。
5. **状态机 / 前置条件层**：每个动作执行前读取「角色-英雄」「角色-军队」等状态，判断将领是否空闲、体力/兵种/兵量是否满足，必要时先修正再执行。
6. **协议执行层**：封装只读查询和真实动作发送，真实动作受 gate 控制。
7. **日志 / 证据层**：底部黑色日志框展示关键动作，报告文件记录真机回归证据。

当前已经完成并真机验证的最小产品闭环是：

```text
登录/session 刷新
  -> 获取角色/资源状态
  -> 获取将领/编队
  -> 找黄
  -> 发送刷黄 prepare(1520030)
  -> 发送刷黄 expedition(1522030)
  -> dispatch-success
  -> dailyLimit 停止
  -> logout
  -> service destroyed
```

## 2. 产品边界与原则

### 2.1 迁移原则

- 优先从小黄点逆向成果迁移机制，而不是凭空重写。
- 只把已经能解释、能测试、能回归的机制产品化。
- 所有真实动作必须经过 gate，不允许绕过开关直接发送。
- 只读查询和真实动作分层，避免误把“看状态”变成“发动作”。
- 状态机是核心：不是只按按钮顺序发包，而是每个动作执行前都必须读取当前状态、校验前置条件、可修正则修正、复查通过后才发真实动作。

### 2.2 真实动作 gate

真实动作目前至少需要同时满足：

```text
realActionNetworkAllowed = true
realActionSendReady = true
realActionScope = brush-yellow
```

刷黄动作限定在 `brush-yellow` scope 内，避免未来日常、占矿、撤防等功能误用刷黄 sender。

### 2.3 native wrapper 处理原则

历史上曾关注小黄点运行时生成的 `lx/key/lb` native wrapper 字段。当前刷黄已验证可通过 direct-binary game command 完成：

- `041540`：找黄 / 地图目标查询
- `1520030`：刷黄 prepare
- `1522030`：刷黄 expedition

所以当前产品策略是：

- 刷黄闭环不依赖小黄点 native wrapper。
- native/session 缺口仍作为后续研究项保留，但不是刷黄阻塞项。

## 5. 核心页面设计

### 5.1 首页 / 托管总览

目标：一眼看到账号状态、当前托管状态、最近日志和高风险 gate。

关键元素：

- 账号卡片：账号、区服、君主名、等级、到期状态。
- 快捷按钮：启动、关闭、修改、添加、删除。
- 状态摘要：session fresh、当前任务、动作前置条件、真实动作 gate。
- 底部日志：必须展示真实协议和状态机日志。

### 5.2 角色状态页

展示从 `0x8004` 解析出的角色状态：

- 君主、等级、国家、称号。
- 铜钱、粮食、声望、人口。
- 资源点占用 / 上限。
- 最近同步时间。

### 5.3 军事页

展示将领和编队：

- 将领列表：名字、ID、状态、体力/忠诚/兵力、当前位置。
- 编队列表：编队 ID、将领、兵力、状态。
- 冲突提示：若将领正在刷黄路上，不能被副本/打矿复用。

### 5.4 刷黄页

这是当前第一个产品化核心功能。

配置项：

- 是否开启刷黄。
- 每日次数 / 本次限制。
- 起始坐标。
- 目标类型：山贼 / 黄巾。
- 目标等级过滤：最低等级、最高等级。
- 编队选择。
- 铜钱保留阈值。
- 是否删邮件提速。

执行链路：

```text
检查 session
  -> 读取角色/资源
  -> 读取将领/编队
  -> 根据配置找黄
  -> reserve 编队
  -> prepare(1520030)
  -> expedition(1522030)
  -> success: 标记 busy + 计数 + Stop/logout 或 Sleep
  -> failed: release reservation + Stop
```

### 5.5 一键日常页

计划承载：

- 签到
- 领取俸禄
- 竞技奖励
- 捐献
- 征收
- 加忠
- 删除邮件
- 任务/成就奖励
- 粮食转铜

当前状态：离线回放/协议 shape 已准备，真实动作未完成。

### 5.6 打矿页

包含两类能力：

1. **找矿只读**：搜索资源点，不发送出征。
2. **自动打矿/占矿**：真实动作扩展，当前仍 gated。

配置项：

- 起始坐标。
- 矿类型。
- 是否只找无人矿。
- 是否只找有驻防矿。
- 命中震动提醒。
- 编队选择。
- 是否撤防。

## 6. 状态机设计

### 6.1 核心定义：状态机 = 动作前状态检查

本项目里的状态机不应优先画成抽象生命周期或全局锁表，而应落到每个动作执行前的“状态读取 + 前置条件判断 + 自动修正 + 复查执行”。

以刷黄为例：

```text
派将领 A 带 10 个轻骑兵去刷黄
  -> 读取「角色 - 英雄」页状态
  -> 读取「角色 - 军队」页状态
  -> 判断将领是否空闲
  -> 判断体力是否足够，不够则使用体力丹
  -> 判断当前统兵兵种是否为轻骑兵，不是则改统领轻骑兵
  -> 判断当前统兵数量是否为 10/最大统兵，不是则改为 10/最大统兵
  -> 复查状态
  -> 找黄 / prepare / 出征刷黄
```

### 6.2 状态来源

状态并不是额外凭空维护一份，而是优先来自当前 App 已经展示的页面：

- 「角色 - 英雄」：将领名、态、类、级、体、忠、统、兵。
- 「角色 - 军队」：编队、将领、状态、兵种、兵力。
- 「刷黄」配置：目标类型、筛选条件、期望兵种、期望兵量。
- 「找黄」结果：目标是否存在、是否新鲜、是否符合配置。

### 6.3 刷黄前置条件

| 检查项 | 状态来源 | 通过条件 | 不通过处理 |
|---|---|---|---|
| 将领状态 | 角色 - 英雄 | `态=闲` | 不自动修正，等待返回或换将 |
| 体力 | 角色 - 英雄 | 体力大于动作最低值 | 使用体力丹，随后复查 |
| 兵种 | 角色 - 军队 | 当前统领兵种 = 配置兵种，例如轻骑兵 | 改统领配置兵种，随后复查 |
| 兵量 | 角色 - 军队 | 当前兵量 = 配置兵量，例如 `10/198` | 调整为配置兵量，随后复查 |
| 目标 | 找黄结果 | 符合筛选条件且 fresh | 重新找黄 |

### 6.4 状态机页面原型

独立原型页：`state_machine_prototype.html`。

该页当前表达的是“动作前状态检查页”：

- 刷黄动作配置：选择将领、目标、兵种、兵量。
- 前置条件列表：逐项展示来源、当前值、是否通过、修正动作。
- 状态来源页：直接复刻「角色 - 英雄」「角色 - 军队」表格。
- 自动修正页：展示体力丹、改兵种、改兵量、复查后执行的链路。

### 6.5 `ff0000` 经验规则

真机验证中发现：

- 同一个将领/目标组合重复使用，可能导致 `1522030 -> ff0000`。
- 原因可能是目标已消灭、将领已出战、状态未刷新或服务器拒绝。
- 因此产品上必须依赖动作前状态检查和 fresh target，而不是固定复用旧样本。

## 7. 协议层分层

### 7.1 GameProtocolClient 接口

所有任务只依赖统一接口，不直接拼接网络请求：

- `login`
- `logout`
- `validateSession`
- `queryMonarch`
- `queryResourceState`
- `queryGenerals`
- `queryFormations`
- `searchMap`
- `dispatchFormation`
- `runDailyStep`
- `searchMines`
- `occupyMine`
- `withdrawMineDefense`

### 7.2 SessionAwareGameProtocolClient

当前真实迁移主要集中在这一层：

- 识别真实 session：`sourceMode == 1`。
- 读取 `channelExtra` 中的 dm、gameHttp、0x8004 payload、将领/编队配置。
- 对只读查询和真实动作做 gate 分流。
- 刷黄 sender 使用 direct-binary game command。

### 7.3 Mock 与真实协议边界

- UI 和大部分任务可使用 Mock 协议跑通流程。
- 已验证的刷黄链路使用真实协议。
- 未验证的日常/占矿/撤防保持 dry-run 或 gated。

## 9. 产品验收标准

### 9.1 刷黄闭环验收

必须同时满足：

- session fresh：`0x1016 -> 0x8004`。
- 能解析角色/资源。
- 能拿到将领/编队。

## 10. 当前风险

1. **0x8004 schema 不完整**：将领是否真正空闲、是否回城、军队状态仍可能误判。
2. **目标复用风险**：旧目标可能已被消灭，重复发送会 `ff0000`。
3. **真实动作范围**：目前只确认刷黄，不能把刷黄 sender 泛化到其它动作。
4. **配置回写**：需要避免 App 启动后旧 UI 状态覆盖外部注入的调试配置。
5. **全量回归缺口**：日常、找矿、占矿、副本等还没有完整真机闭环。

---

## 11. 建议的下一个产品化步骤

优先建议：**补全 0x8004 状态 schema**。

原因：

- 它是所有任务状态机的底座。
- 能降低刷黄 `ff0000`。
- 后续打矿、副本、日常都依赖准确的将领/军队状态。

具体拆分：

1. 从 0x8004 payload 中标注将领结构起止位置。
2. 解析将领：ID、名字、状态、体力、兵力、位置、返回时间。
3. 解析军队/编队状态。
4. 把解析结果接入 `queryGenerals` / `queryFormations`。
5. 状态机根据真实返回时间释放锁，而不是只靠本地推断。
