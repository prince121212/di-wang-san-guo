# 2026-09-19：共享云端额度阻断出征的根因与修复

## 第一性原理

四队吞吐受游戏闭环、客户端独立调度、可派遣目标供给和云端可写性共同约束。
扩大搜索范围不能解决“目标已找到，但预占不能写入”的阻塞；在共享模式下，
无成功的原子预占就不能安全派遣，缩短 sleep 或绕过预占只会制造冲突。

V103/V104 已修复独立编队、旧目标反复领取、错误归属和假恢复。本文处理其后
仍使真实出征停滞的云端依赖，不把离线测试通过当成实际吞吐恢复。

### 3. “增量”查询仍在扫描存量

15:29:13的查询分析中，旧 changes SQL 约343次调用、读取3,201,416行，
占当时读取的大部分。

在同一生产数据库、相同最新游标上做两次只读对照，均返回0条：

| 条件 | 执行计划中的范围 | 实际 rows_read |
| --- | --- | ---: |
| `changed_at > ? OR (changed_at = ? AND target_id > ?)` | 仅 server_key/map_kind 前缀 | 14,465 |
| `(changed_at,target_id) > (?,?)` | 前缀 + 复合游标范围 | 2 |

这些是 D1 实际返回的读行数；没有假目标、写入探针或清表。它证明的是查询
成本下降，不是“出征速度提高了同样倍数”。

## 修复

1. **服务端重复交付不重复写**：规范化后的有效目标没有字段变化时，不改行、
   last_seen_at 或 changed_at。真实变化和合法复活立即执行；已过期记录可被
   相同观察续期，避免因优化而卡在 TTL 后。活动预占及在途状态保持。
2. **消失事件幂等**：已是 missing 的目标不重复写墓碑，不让空重试不断产生
   假增量；reserved/dispatching 的原保护保持。
3. **单批原子提交**：upserts、gone、旧链接清理共用一个 D1 batch；
   任意一步失败全部回滚，HTTP成功才代表整批已接收。
4. **参数数目有界**：gone 使用 json_each，200个 ID 不再超过100参数上限。
   本次 upsert/gone/清理三条语句最多分别11/5/4个参数。
5. **真正按变化定位**：changes 使用现有复合索引的行值范围，无 schema 改动。
6. **暴露可行动的容量错误**：识别直接/包装的 D1 日读写限额异常，
   返回 HTTP503、`CLOUD_D1_DAILY_LIMIT`、UTC重置时间与 Retry-After；
   不暴露 SQL，不把其他异常冒充成额度问题。

不改账号筛选、将领、配兵、每日上限或启停；不删失败队列，不绕过预占，
不把任何不确定游戏发送改成成功。手机继续使用 V0.0.104，无需重装。
