# V0.0.103：刷黄编队独立调度

## 第一性原理

账号的协议请求必须串行，防止 Session、资源和出征回执串账；但是网络请求结束
不等于游戏中的战斗结束。收到确认回执后，真正仍被占用的是本次出征的将领与
目标，不是整个刷黄功能。

因此不通过放宽山贼筛选、扩大扫描量、关闭防重或并发发送协议提高表面吞吐：

1. 一次只发送一条账号协议请求。
2. 不同将领的编队可以同时在外作战。
3. 每次出征保有自己的将领、目标、battleId、发送边界、维护进度和下次观察时间。
4. 只有确认该队回闲且战后维护完成，才释放该队将领。
5. 一队等待、缺资源或回执不明，只约束该队；无关编队继续调度。

## 改动

- `brushPendingRecoveryJson` 明确为当前执行槽，不再代表整个账号的刷黄占用。
- `brushWaitingRecoveriesJson` 保存其他在途/恢复/待核对记录；以稳定的
  `recoveryKey` 标识一次出征（正式派遣前即存在，取得 battleId 后不换身份）。
- 切换执行槽和等待集合是同一次账号持久化写入。原有逐步骤 sending/uncertain/
  accepted 账本继续使用执行槽，清理只作用于选中记录，不清除其他编队。
- 旧单条账本无需手工清理，首次接管赋予稳定身份，后续出征原样保留它。
- 派遣前按待决账本占用的将领跳过冲突规则；所有出征共用的预检也检查刷黄占用。
  已知忙碌的其他功能将领不抢占空闲规则；全忙时重新读取，防止旧缓存永久冻结。
- 当前账号已出征的目标从扫描结果和缓存候选中排除，直接出征入口也执行防重。
  云端原子预占与真实游戏回执保护不变。
- 按各记录自己的期限调度恢复；保留其他编队的派遣游标和期限。独立编队之间
  默认保留 1 秒业务间隔，平台及协议限速不变；战后观察仍为 30 秒。
- 确认回执和当日计数原子落盘；成功记录恢复读取全部编队账本，不只读一个槽位。
- 不确定治疗结清后的“一次跳过治疗”按将领保存，不能被另一队消耗。
- 各队的异常/资源等待保留可忽略提示；旧版桌面待决检测也包含等待集合，人工
  单步结清一队不能错误宣布全部账本已清空。
