## 第一性原理与修复 / Root cause and changes

### 1. 网络请求的粒度不等于用户任务的粒度

已验证的 `0x1103` 丢弃包只有一个对象 ID：
`kind:u8 + objectId:i64 + count:i32 + tail:i64`。
装备实例不能通过把 count 改成 5 来冒充五把不同短剑。

现在把“清完符合条件的库存”作为持续任务：

- 每次调度最多推进 **5 个动作**；已用时达到 **5 秒**时不再启动下一动作。
  已经发送的单个网络请求仍遵守原有超时和结果核对，不强行中断。
- 每件先持久化发送账本，再发送、确认、记账，之后才处理下一件。
- 完整、刚收到的成功 `0x8103` 库存可用于确认和本批下一件规划，减少重复刷新。
  缺少完整库存则只读刷新；跨重启不会拿旧回包当新库存。
- 批间释放账号执行机会；续批在到期且等待约 10 秒后参与公平调度，
  不再每一件都重新等待 10 分钟。军务正常优先级、未来截止时间和未知结果隔离仍有效。
- 兼容 V99 已持久化但没有续批标记的未完成清理轮次。
- 一段达到原有 50 动作上限但仍有垃圾装备/道具时，短暂让出后继续下一段，
  不睡一小时；自动开启数量预算和本轮拒绝目标跨段保留。
- 新掉落的同一种道具不能一直抢在所有装备前面：一次道具丢弃后，
  若该道具再次出现且有可清理装备，先让装备获得一次机会。

### 2. 明确拒绝与结果未知必须分开处理

- 明确服务器拒绝：保留原因、本轮跳过该目标，继续其他目标，不记录成功。
- 回执未知、成功状态但库存未变化、库存不完整：停止本批变更，保留账本，
  后续只读核对，绝不为了“清完”盲目重发。
- 品质选择、等级 36 边界、名将装备、强化、炼魂/额外描述及元数据保护不变。

### 3. 展示数量必须由已确认事实相加

- 每件独立保留原始成功记录与 actionKey / instanceId。
- 记录页只在展示时合并同一轮、同名、同品质、同等级的已确认记录，
  数量来自实际 consumedCount；不同轮次和旧版无轮次标识记录不猜测合并。
- 合并详情保留各件动作证据，读取页面不会压缩或改写原始账本。
- 修复零道具格时把后面的装备字节误扫成道具的问题。
- 补齐 Android 轻量账号投影的容量解析版本标记、实际占用格数及数量字段，
  避免后台已经读到 50 的上限，页面却因丢失标记显示“尚未读取”。
